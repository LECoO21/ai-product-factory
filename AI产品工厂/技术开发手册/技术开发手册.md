## 〇、开发总则（所有任务共同遵守）

1. **不动现有边界**：不采用 Subagent / Memory / Agent Teams / Cron / MCP，不执行真实发布，不删除或重建 SQLite 数据，不修改三份原始手册。
2. **每个任务独立可验收**：做完一个、验收通过，才进入下一个；有依赖的必须等前置完成。
3. **改一处、全生效**：新增规则要集中在统一位置，不散落复制。
4. **每步都记账**：状态变化、工具调用、权限裁决、审批决定都要写入 SQLite，重启可恢复。
5. **工程检查命令**（每个任务完成后都要跑）：
   ```bash
   npm run lint
   npm run typecheck
   npm test
   npm run test:e2e
   npm run build:vefaas
   npm run manuals:verify
   ```

## 一、P0-1 返工循环（最优先）

### 目标

让 Harness 在"检查未通过"时**自动再驱动 Agent 一轮**，直到完成目标或轮数用尽。大白话：工人没做好就自动返工。

### 现状

- `factory-harness.ts` 的 `run()`：`driver.run()` 跑**一轮** → `verifier.verify()`。
- `verifier.verify()` 返回 `continue`（证据不足）时，代码走 `else` 分支直接 `failed`，**没有再次调用 `driver.run()`**。
- 也就是说，当前"失败 → 修复 → 复测"只能靠 prompt 里手把手要求 Agent 在一轮内完成，Harness 机制本身不兜底。

### 改动点

1. 在 `FactoryHarness.run()` 里把"跑一轮 → 验证"改成**循环**：
   ```
   第 1 轮：driver.run() → verifier.verify()
   结果 = continue → 把 missing/failed 清单拼进下一轮 prompt → 第 2 轮
   结果 = complete → succeeded
   结果 = failed → 终止失败
   结果 = 轮数用尽 → 终止并如实报告
   ```
2. 新增"轮数上限"配置（例如默认 3 轮，可通过常量或环境变量调整）。
3. 每一轮的结果、验证结论、失败/缺失清单都写进 SQLite，不覆盖上一轮。

### 关键设计

- **循环由代码控制**，不依赖 Agent 自觉；Agent 只负责"按本轮 prompt 干活"。
- **下一轮 prompt 必须携带**：上一轮的验证结论 + 具体缺失哪几项证据 + 要求补齐的最小目标。不能让 Agent 从零重新开始。
- **轮数上限是硬性安全阀**：防止无限循环烧钱。
- `verifier.verify()` 的 `continue` 语义保持不动，由 `FactoryHarness` 负责把它翻译成"再跑一轮"。

### 验收

- 单元测试：给一个"第一轮必缺证据"的 mock 场景，断言会跑第二轮，且第二轮 prompt 包含缺失清单。
- 单元测试：轮数用尽后返回 `failed`，且 summary 里说清"几轮未达标"。
- 真实验收：`executeHarnessValidation` 的 fixture 里，第一轮故意失败，Agent 能在循环内修复并复测通过，全程不打扰用户。

## 二、P0-2 危险动作审批

### 目标

让 P2 工具从"直接拒绝"变成"挂起 → 页面展示 → 用户同意/拒绝 → 恢复执行"。大白话：危险动作停下来问用户。

### 现状

- `tool-gateway.ts` 的 `execute()`：P2 工具直接 `finish("approval_required", "该重大动作需要重新确认生产单，未执行")` 一次性拒绝返回。
- 已有基础：工具状态已有 `approval_required`，Harness 状态已有 `waiting_user`，FactoryHarness 已有 `suspended` outcome（对应 `waiting_user`）。
- 缺的是完整闭环：暂停后等用户批准、批准后恢复执行"这一件动作"、拒绝后回传 denied 让 Agent 换路，以及对应的 Web API。

### 改动点

1. **复用已有状态，不新造**：工具用 `approval_required` 表示等待审批，Harness 用 `waiting_user` 表示挂起，不引入新状态名。
2. 当某次工具调用进入 P2 审批时，让整个 Harness 进入 `waiting_user`（挂起），审批请求写入 SQLite。
3. 新增 Web API：读取待审批请求、批准、拒绝。
4. 批准 → 恢复 Harness，该工具标记已批准并继续；拒绝 → 该工具标记 `denied`，Agent 换路。

### 关键设计

- **审批对象是"这一次具体动作"**，不是"重新确认整个生产单"。换目标、换内容、换费用后必须重新审批。
- 挂起期间，同一 Harness 的其他工具调用也停止，不能绕过。
- 审批请求要记录：工具名、脱敏参数、影响说明、是否计费、能否反悔、审批状态、时间。
- 批准/拒绝决定写进 SQLite，可审计。

### 验收

- 单元测试：P2 工具返回 `waiting_approval`，Harness 进入挂起态，记录审批请求。
- 单元测试：批准后 Harness 恢复，工具结果标记已批准；拒绝后工具结果标记 denied。
- 集成测试：删除/花钱类工具在页面上触发审批，用户批准后执行、拒绝后不执行，全程留痕。

## 三、P1-1 独立检查员

### 目标

把"完成判定"升级成独立的判断器：能给出 continue / complete / failed / impossible（目标做不到），且不依赖 Agent 自评。

### 现状

- `completion-verifier.ts` 只查证据表 + 文件 hash 校验 + 检测 pending 工具。
- 没有"目标不可能"判定，没有预算/轮数超限判定，`continue` 结果目前被上层当成 failed。

### 改动点

1. 扩展 `CompletionVerifier` 的返回类型，加入 `impossible`（目标不可达成）与 `budget_exhausted`（预算/轮数用尽）。
2. 判定依据只看 SQLite 里的真实证据、产物 hash、工具结果，**不接受 Agent 文字自评**。
3. 与 P0-1 的循环打通：`continue` → 再跑一轮；`impossible` / `budget_exhausted` → 终止并交还用户；`complete` → 成功。

### 关键设计

- 检查员与 Agent 是两套代码，不共享状态。
- "目标不可能"的判断依据要可解释：例如关键依赖永远缺失、错误重复出现且无法修复、完成目标与产物类型冲突。
- 预算/轮数超限时如实报告，不假装成功。

### 验收

- 单元测试：无证据时返回 continue；证据完整且 hash 一致时返回 complete；关键依赖永久缺失时返回 impossible；轮数/预算用尽时返回 budget_exhausted。
- 集成测试：Agent 声称完成但没有证据时，检查员返回 continue，Harness 继续驱动。

## 四、P1-2 统一小关卡（Hooks）

### 目标

把散落在 `tool-gateway.execute()` 里的记账、脱敏、防越界、权限检查，抽成统一的 PreToolUse / PostToolUse 关卡。

### 现状

- `tool-gateway.ts` 的 `execute()` 内联了：`pathViolation`、`redactArgs`、权限判断、`startInvocation` / `completeInvocation`。
- 规则写死在执行方法里，新增工具或新增规则都要改这里，容易漏。

### 改动点

1. 定义两个关卡接口：
   - **PreToolUse**：执行前，可返回"允许 / 阻断"。承载：权限判断、schema 校验、路径越界、秘密文件拦截。
   - **PostToolUse**：执行后，承载：结果登记、记账、脱敏、证据候选。
2. `ToolGateway.execute()` 改成"过 Pre 关卡 → 执行 → 过 Post 关卡"的固定骨架。
3. 现有逻辑迁移进关卡，不改变行为，只改变组织方式。

### 关键设计

- 关卡可注册、可组合，规则集中在一处。
- Pre 关卡可阻断，Post 关卡异常不影响主结果记录。
- 新增工具自动经过关卡，无需重复写检查。

### 验收

- 单元测试：新增一个工具，不写任何检查逻辑，仍自动获得脱敏、路径越界、记账能力。
- 回归测试：现有 `tool-gateway.test.ts`、`manual-authority.test.ts` 等全部通过，行为不变。

## 五、P1-3 断电续干

### 目标

让任务、租约、检查点、依赖关系持久化，Worker 重启后从安全位置接着干，不重复、不丢失。

### 现状

- 有 `createTask` / `updateTask` / `recoverRunningRuns` 的基础。
- 缺：任务依赖图、租约续期、检查点、副作用记录、Workflow journal。
- `BackgroundRunner` 有 `recoverAfterRestart`，但只处理后台任务，不覆盖整个生产流程。

### 改动点

1. 任务表增加依赖关系字段（一个任务依赖哪些任务）。
2. 增加"租约"：任务被认领时记录认领者与过期时间，超时自动回收。
3. 增加"检查点"：每完成一个原子步骤记录安全位置。
4. 增加"副作用记录"：恢复前先查上一动作是否已生效，避免重复扣费/发布。
5. Worker 启动时按 journal / 检查点恢复，而不是从头开始。

### 关键设计

- 同一件活同一时间只允许一个认领者。
- 恢复使用稳定调用键，已完成的副作用不重复执行。
- 所有持久化走现有 SQLite Store，不引入新存储。

### 验收

- 单元测试：任务认领后重启，租约回收，恢复时从检查点继续。
- 集成测试：模拟 Worker 中途崩溃，重启后不重复执行已完成的副作用，从上次安全位置继续。

## 六、P2-1 危险动作开关自动化

### 目标

把 P1 工具的放行从"手工布尔 `p1Approved`"改成绑定已确认的闸门状态。

### 现状

- `apps/worker/src/index.ts` 的 `executeHarnessValidation` 里写死 `p1Approved: true`。
- 放行与"G6 已确认"等闸门状态没有真实绑定。

### 改动点

1. 让 `ToolGateway` 的 P1 放行条件改为：读取当前生产批次是否已通过对应闸门（如 G6）。
2. 移除硬编码 `p1Approved: true`，改为从 SQLite 的确认状态推导。
3. 闸门过期或失效后，P1 自动回到不放行。

### 关键设计

- 放行依据是持久化的确认事实，不是运行时布尔。
- 确认版本变化后，旧的放行随之失效。

### 验收

- 单元测试：未确认时 P1 工具被挡；确认后放行；确认过期后再次被挡。
- 回归测试：`executeHarnessValidation` 在已确认前提下仍能通过。

## 七、P2-2 工具干完自动记账

### 目标

工具执行后自动登记结果与证据候选，不依赖 Agent 主动调用 `evidence.register`。

### 现状

- `tool-gateway.ts` 已自动写 `startInvocation` / `completeInvocation`（工具账）。
- 但"证据"目前靠 Agent 主动调用 `evidence.register` 工具上报。

### 改动点

1. 在 PostToolUse 关卡里，根据工具结果自动生成"证据候选"（例如 `test.run` 成功 → 自动登记一条 passed 证据候选）。
2. 证据候选仍需经过 hash 校验与完成目标关联，最终是否通过由独立检查员判定。
3. 保留 Agent 主动登记的入口，但自动候选是基础。

### 关键设计

- 自动记账 = 工具执行事实；证据判定 = 检查员职责，两者分离。
- 自动候选不能代替"完成目标关联"，避免错误证据。

### 验收

- 单元测试：`test.run` 成功后，SQLite 里自动有证据候选记录，无需 Agent 主动调用。
- 集成测试：检查员能读取自动候选并据此判定，而非只听 Agent 上报。

## 八、P2-3 自动清记录

### 目标

实现上下文清理：旧工具大结果转存、普通历史摘要、权威内容永不删。

### 现状

- 三份手册全文直接拼进 prompt，没有上下文预算、结果裁剪、历史摘要机制。

### 改动点

1. 增加上下文管理模块（ContextManager）：
   - 旧的大段工具结果 → 转存为产物并保留引用，从上下文移除。
   - 普通历史 → 摘要后保留。
   - **三份手册、当前目标、重大决定、未解决错误 → 永不压缩、永不删除。**
2. 在每轮循环前应用清理，记录压缩前后的 Token 指标。

### 关键设计

- 权威手册走独立通道（ManualAuthority），ContextManager 不得触碰。
- 清理前后记录 Token 与缓存指标，便于观测成本。

### 验收

- 单元测试：长历史被摘要、旧工具结果被转存、手册与目标原样保留。
- 集成测试：长任务运行后，关键决定与未解决错误仍在上下文中。

## 九、公共数据结构约定

以下字段/状态在多个任务中共用，统一约定，避免各自造轮子：

| 概念 | 统一表示 | 说明 |
| --- | --- | --- |
| Harness 运行状态 | `ready / running / verifying / waiting_user / succeeded / failed / cancelled / interrupted` | 复用现有 HarnessRun 状态；P0-2 用 `waiting_user` 表示挂起审批 |
| 工具结果状态 | `started / succeeded / failed / approval_required / denied` | 复用现有状态；P0-2 用 `approval_required` 表示等待审批，不新增 |
| 完成判定 | `continue / complete / failed / impossible / budget_exhausted` | P1-1 新增 `impossible` 与 `budget_exhausted` |
| 轮数上限 | 常量 + 可配置 | P0-1 引入 |
| 租约 | `ownerId + expiresAt`（现有 task 表已有 `worker_id`，需补 `expires_at`） | P1-3 引入 |
| 检查点 | `checkpointId + stage + status` | P1-3 引入 |

## 十二、完成状态与架构变更（2026-09-04 更新）

### 架构变更：Codex → DeepSeek

原方案以 Codex App Server 作为唯一 Agent 运行时（见 ADR 0002）。经产品负责人决定，**所有生产流程改为 DeepSeek V4 Pro**：

- 技术环节（接单/适配/计划/制作/发布方案）→ DeepSeek 纯文本生成。
- Harness 验证（改文件/跑测试）→ DeepSeek function calling 调用工具。
- 登录闸门 → `FACTORY_AUTH_BYPASS=true` 绕过（不再需要 OpenAI 登录）。

涉及文件：
- 新增 `packages/agent-runtime/src/deepseek-runtime.ts`。
- `apps/worker/src/index.ts`：技术环节与 Harness 验证均改用 DeepSeek。
- `.env`：`FACTORY_AUTH_BYPASS=true`、`DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL=deepseek-v4-pro`。
