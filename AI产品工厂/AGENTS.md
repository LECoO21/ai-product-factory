# 三手册优先协议

## 最高工程规范源

开始任何产品分析、方案设计、编码、审查、测试、部署或交付前，完整读取以下三份原始手册；每次都以原文件全文为准：

1. `../AI产品Vibe Coding通用技术栈手册.md`
2. `../AI产品Vibe Coding通用前端技术栈手册.md`
3. `../AI Agent 产品上线部署手册.md`

这三份原始文件是项目的工程宪章。`README.md`、`CONTEXT.md` 和 `docs/` 中的项目文档只记录本项目事实、适配结论与追踪关系，不能替代、删减、压缩或改写三份手册的要求。

公开仓库不分发三份原文。工作区缺少原文时，停止需要手册约束的规范性开发并请求内部资料；不能用公开摘要代替。

## 每次工作的固定顺序

1. 在仓库根目录运行 `npm run manuals:verify`；只有三份原文完整性全部通过，才能继续。
2. 根据任务阶段完整读取对应手册；跨阶段任务完整读取三份。读取摘要、节选、旧副本或项目派生文档不算完成。
3. 按手册先完成环境与现有代码自检，再输出或更新《技术适配声明》和当前阶段开发文档。
4. 手册要求产品经理确认的闸门必须等待确认；确认后只实现当前阶段。
5. 按手册执行自动检查、真实浏览器验收和真实模型冒烟；没有 Key 时把真实冒烟标记为待验。
6. 交付前再次运行 `npm run manuals:verify`，并逐条更新手册追踪记录。

## 冲突与适配

- 业务行为遵循本轮明确目标和已确认 PRD；安全、隐私、数据保护、可恢复性与验收真实性遵循三份手册的强制底线。
- 手册默认方案因现有代码、部署环境或 PRD 需要调整时，在《技术适配声明》中写明原条款、替代方案、原因、影响和重新评估条件。
- 项目文档与原始手册冲突时，以原始手册全文和手册内部的冲突处理规则为准，并修正项目文档。
- 修改任一原始手册后，必须由产品负责人确认，并同步更新 `docs/MANUALS.sha256`；普通项目开发不得改动原始手册。

## 交付证据

每次阶段交付必须列出：采用的手册条款、验证证据、未通过项、真实模型冒烟状态，以及所有经过确认的偏离。只有可追溯到原文的结论才可作为闸门证据。
