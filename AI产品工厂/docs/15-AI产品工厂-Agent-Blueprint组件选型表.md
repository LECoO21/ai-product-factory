## 1. G4 推荐结论

第一版不把 Agent Blueprint 的 17 个组件全部装进工厂。

推荐结果：

- **采用 12 项**：s01、s02、s03、s04、s05、s07、s08、s10、s11、s15、s16、s17；
- **暂缓 3 项**：s06、s09、s13；
- **当前不采用 2 项**：s12、s14；
- **工厂自身采用 4 类能力包**：Web 交互、Agent 运行、长任务、高风险动作；
- **工厂自身当前不采用 5 类能力包**：RAG、多媒体生成、游戏体验、账户多租户、实时通信。

这个组合足以让单个工厂 Agent 在确定性控制平面内连续行动、调用工具、恢复任务并用真实证据完成目标，同时不提前承担多 Agent 团队、跨项目记忆、定时自治和外部工具生态的复杂度。

## 2. 选型规则

每个候选项按以下顺序判断：

1. 已确认 PRD 或 G3 五要素是否明确需要它；
2. 删除它后，核心闭环会在哪个具体位置失败；
3. 现有 Module 是否已经承担了部分责任，能否延续而不是重建；
4. 是否会新增外部平台、费用、数据上传或运维负担；
5. 能否通过一个小而清晰的 **Interface** 隐藏复杂 **Implementation**；
6. 是否存在真实变化点，值得建立 **Seam** 和多个 **Adapter**；
7. 如果当前没有真实需求，则暂缓或不采用，不为“架构完整”预装。

其中：

- **Module**：拥有一个 Interface 和内部 Implementation 的落地模块；
- **Interface**：调用方必须知道的全部规则，包括输入、顺序、错误、配置和性能约束；
- **Seam**：可以替换行为而不修改调用方的位置；
- **Adapter**：在 Seam 上满足 Interface 的具体实现。

## 3. Agent Blueprint 17 项选型总表

| 编号 | Agent Blueprint 候选项 | G4 结论 | 触发的产品事实 | 没有它会在哪里失败 | 当前落地要求 |
| --- | --- | --- | --- | --- | --- |
| s01 | Agent Loop | 采用 | 工厂 Agent 要连续推理和使用工具，不是一次生成文本 | 每个生产单只能得到一段回答，无法真实修改、验证和继续 | 延续 Pi Agent 驱动循环，经工厂 AgentRuntime 隔离 |
| s02 | Tool Use | 采用 | G3 已确认文件、Git、Shell、测试、浏览器和产物工具 | Agent 无法作用于外部世界，工厂仍是聊天产品 | 统一工具注册、schema、错误结构、副作用和结果配对 |
| s03 | Permission | 采用 | 工厂会写文件、执行命令、访问模型并准备发布 | 路径越界、秘密泄露、破坏性命令和外部发送无法可靠阻止 | 执行前默认拒绝，落实 P0–P3、人工闸门和审计 |
| s04 | Hooks | 采用 | 权限、审计、用量、证据和产物登记横跨全部工具 | 相同规则散落在每个工具里，容易漏记、漏拦截和不一致 | PreToolUse 可拦截；PostToolUse 统一记录观察和副作用 |
| s05 | TodoWrite | 采用 | 单次产品生产有多步计划，用户要看懂当前目标和下一步 | Agent 容易忘记计划，用户只看到长日志，不知道进度 | 保存本轮可见计划；它不是持久生产任务的事实来源 |
| s06 | Subagent | 暂缓 | 当前先验证单 Factory Agent，尚无真实上下文隔离瓶颈 | 当前不会导致核心闭环失败 | 单 Agent 达到明确质量或上下文瓶颈时再评估 |
| s07 | Skill Loading | 采用 | 产品类型不同，领域规则和能力包必须按需加载 | 所有知识被塞进同一 Prompt，成本上升并产生产品污染 | 目录先行、按需加载、版本可追踪；手册原文走独立权威通道 |
| s08 | Context Compact | 采用 | 三份手册很长，生产任务还会产生大量工具结果 | 上下文溢出，Agent 丢失目标、历史动作或工具配对 | 先裁旧工具大结果，再摘要普通历史；权威手册不可压缩 |
| s09 | Memory | 暂缓 | 第一版只要求项目内档案可恢复，没有跨项目偏好复用 | 当前不会导致核心闭环失败 | 先用生产档案和已确认版本，不自动形成跨项目记忆 |
| s10 | Task System | 采用 | 长任务要依赖、认领、暂停、恢复并避免重复副作用 | Worker 重启后丢任务，无法可靠断点续跑 | 持久任务图、原子状态、租约、依赖和恢复 |
| s11 | Background Tasks | 采用 | 安装、构建、测试和浏览器验收可能较慢 | Agent Loop 或 Web 请求被长时间阻塞，无法观察和取消 | 后台执行、完成通知、超时、取消和残留进程清理 |
| s12 | Cron Scheduler | 不采用 | 第一版所有生产由用户主动发起 | 删除它不影响任何已确认流程 | 不建立定时调度；出现明确定时巡检或生产需求再重新走 G4 |
| s13 | Agent Teams | 暂缓 | 当前单用户、单 Worker、单写入者优先保证安全 | 当前不会导致核心闭环失败，过早并行反而增加冲突 | 单 Agent 吞吐成为已测瓶颈并具备 worktree 隔离后再评估 |
| s14 | MCP Plugin | 不采用 | 当前核心工具都可以由本地受控工具提供 | 删除它不影响第一版核心闭环 | 不连接外部 MCP；目标产品必须接外部生态时重新评估 |
| s15 | Integrated Harness | 采用 | Agent Loop、工具、权限、Hooks、任务和上下文必须协同 | 多套循环和事件模型彼此分裂，状态与权限难以一致 | 所有机制归入一个 FactoryHarness Module，不复制循环 |
| s16 | Workflow Runtime | 采用 | G1–G9 是固定、可追踪、可恢复的生产编排 | 阶段顺序只存在聊天里，刷新或重启后无法可靠继续 | 代码拥有阶段编排，journal 记录生命周期，Agent 只决定阶段内行动 |
| s17 | Goal Loop | 采用 | 模型停止不等于完成，必须依据产物、测试和人工验收 | 空结果、半成品或失败结果可能被误判为完成 | Goal Gate 独立检查完成目标、证据、预算和不可能状态 |

## 4. 采用项如何组成最小 Harness

### 4.1 行动内核

| Module | 包含的蓝图项 | 对外 Interface 应隐藏什么复杂度 | 主要调用者 |
| --- | --- | --- | --- |
| FactoryHarness | s01、s15 | Pi Agent 事件、上下文更新、工具回传、退出原因和循环细节 | Worker / Workflow Runtime |
| ToolGateway | s02、s03、s04 | 工具发现、schema 校验、权限、Hooks、超时、错误和结果登记 | FactoryHarness |
| WorkPlan | s05 | 本轮计划项、状态和用户可见进度的维护规则 | FactoryHarness / WebUI |

删除 FactoryHarness 后，循环、工具回传、上下文和退出处理会重新散落到 Worker；删除 ToolGateway 后，权限、校验和审计会重新散落到每个工具。两者都通过删除测试，因此值得成为深 Module。

### 4.2 知识与上下文

| Module | 包含的蓝图项 | 对外 Interface 应隐藏什么复杂度 | 特别约束 |
| --- | --- | --- | --- |
| KnowledgeLoader | s07 | 能力包目录、版本、按需加载和来源追踪 | 目标产品知识只能进入对应项目 |
| ContextManager | s08 | Token 预算、工具结果裁剪、普通历史摘要和恢复 | 未完成目标、工具配对和检查点必须保留 |
| ManualAuthority | 工厂专用强制 Module | 手册定位、SHA 校验、阶段选择、稳定顺序和加载记录 | 三份手册不是普通 Skill，不参与摘要替代 |

ManualAuthority 不是 Agent Blueprint 新增组件，而是三份手册最高优先规则在本项目中的专用 Module。它必须独立于普通 Skill 和 Context Compact，避免通用压缩逻辑误删权威原文。

### 4.3 持久任务与固定编排

| Module | 包含的蓝图项 | 对外 Interface 应隐藏什么复杂度 | 与其他 Module 的关系 |
| --- | --- | --- | --- |
| TaskSystem | s10 | 任务依赖、租约、认领、幂等、检查点和恢复 | 保存生产阶段内外的持久任务事实 |
| BackgroundRunner | s11 | 慢任务进程、完成通知、取消、超时和清理 | 只执行 TaskSystem 已登记的受控任务 |
| WorkflowRuntime | s16 | G1–G9 阶段脚本、journal、暂停、继续和版本失效 | 驱动 FactoryHarness，不进入内部工具决策 |

s05 WorkPlan 与 s10 TaskSystem 不合并：前者是 Agent 本轮工作的可见计划，后者是生产控制器拥有的持久任务事实。把二者混成同一状态会让模型可以改写生产生命周期。

### 4.4 完成判定

| Module | 包含的蓝图项 | 对外 Interface 应隐藏什么复杂度 | 输出 |
| --- | --- | --- | --- |
| GoalGate | s17 | 完成目标、证据完整性、预算、失败、不可能和人工决定 | 继续 / 完成 / 失败 / 等待用户 |

GoalGate 只读取已登记事实，不直接运行工具，也不接受 Factory Agent 的自评作为通过依据。

## 5. Module 之间的责任线

```text
WorkflowRuntime 选择当前已确认阶段和完成目标
→ FactoryHarness 驱动一个 Agent Loop
→ KnowledgeLoader / ManualAuthority 提供当前必要知识
→ FactoryHarness 经 ToolGateway 请求行动
→ ToolGateway 完成权限、Hooks、执行与结果登记
→ TaskSystem / BackgroundRunner 保存并运行长任务
→ GoalGate 用产物和证据判断继续还是结束
→ WorkflowRuntime 根据确定性结果进入等待确认或下一阶段
```

责任线必须满足：

- WorkflowRuntime 不解释模型文本来猜阶段；
- FactoryHarness 不直接写数据库或绕过 ToolGateway；
- ToolGateway 不决定整个生产目标；
- WorkPlan 不等于 TaskSystem；
- ContextManager 不压缩 ManualAuthority 内容；
- GoalGate 不调用发布工具，也不自行替产品负责人确认；
- WebUI 只显示后端状态，不通过计时器或动画伪造完成。

## 6. 暂缓项及重新评估条件

### 6.1 s06 Subagent

当前原因：单 Factory Agent 尚未完成第一台真实产品试产，无法证明多一个 Agent 能解决真实问题。

重新评估需要至少出现一项事实：

- 单次任务上下文因独立审查、研究或大规模日志而持续超限；
- 把一个子任务隔离后，真实质量或成本数据明显优于单 Agent；
- 子任务有明确输入输出，失败不会污染主任务；
- 已具备超时回收、工具权限继承和最终结果回传规则。

### 6.2 s09 Memory

当前原因：项目内的 PRD、决定、产物和事件由生产档案持久化，已满足恢复；暂时没有跨项目自动记住偏好的需求。

重新评估条件：产品负责人明确要求跨项目复用偏好或决定，并能定义什么允许记住、如何查看修改、何时过期和怎样避免项目间数据污染。

### 6.3 s13 Agent Teams

当前原因：第一版单用户、单 Worker、单写入者，优先解决可靠性。当前工作区也存在大量未提交改动，过早并行会增加覆盖和合并风险。

重新评估需要：

- 单 Agent 已通过真实试产但吞吐成为可测瓶颈；
- 任务可被稳定拆成互不覆盖的工作区；
- 每个队友拥有独立 worktree、原子认领、邮箱协议和关停流程；
- 多 Agent 的成本、质量和恢复测试优于单 Agent。

## 7. 当前不采用项

### 7.1 s12 Cron Scheduler

PRD 没有定时生产、定时巡检或无人触发任务。第一版由产品负责人主动开始生产，因此 Cron 没有调用者，也没有失败位置。

只有新增明确的定时业务目标、时区、重试、幂等和通知规则后，才重新进入组件选型。

### 7.2 s14 MCP Plugin

第一版所需的文件、Git、Shell、测试、浏览器、产物和人工闸门都可以由本地 ToolGateway 提供。当前没有已确认的外部 MCP server、工具发现或跨系统认证需求。

如果未来某个目标产品必须接入外部工具生态，先在该产品 PRD 中确认数据范围、权限、费用和失败降级，再把 MCP 作为该目标产品能力包重新评估；不能因为 Agent Blueprint 提供了参考实现就预装。

## 8. 工厂自身的能力包选择

能力包表达产品差异，不等于 Agent Blueprint 的 s01–s17 运行组件。

| 能力包 | G4 结论 | 触发事实 | 没有它会在哪里失败 |
| --- | --- | --- | --- |
| Web Interface | 采用 | 第一版是可控制、可观察、可确认的对话式 WebUI | 用户没有说需求、看结果、恢复任务和确认的入口 |
| Agent Runtime | 采用 | Pi Agent + DeepSeek 是工厂主体 Agent 与主要模型 | 工厂只能执行固定规则，无法动态规划阶段内动作 |
| Long-running Task | 采用 | 产品生产、安装、构建、测试和验收跨越短请求 | 页面刷新或 Worker 重启后任务丢失 |
| High-risk Actions | 采用 | 文件写入、Shell、Git、外部发送和发布存在风险 | 无法落实 P0–P3 权限和重大影响确认 |
| RAG | 不采用 | 当前知识是有限的版本化手册、PRD、代码和能力包 | 删除后不影响第一版；直接读取和搜索即可 |
| Multimedia | 不采用 | 工厂自身当前不生成图片、音频或视频作为核心能力 | 目标产品需要时由对应产品能力包引入 |
| Game Experience | 不采用 | 小游戏只是试产对象，不是工厂产品形态 | 工厂内核不应包含关卡、得分或游戏体验规则 |
| Accounts and Tenancy | 不采用 | 第一版唯一用户是产品负责人本人 | 单用户本地版本不需要登录和租户隔离 |
| Realtime Communication | 不采用 | SSE 只用于单向观察，不存在语音、协作或双向高频通信 | 普通 HTTP + SSE 足够当前 WebUI |

### 8.1 目标产品能力包规则

以后每接入一个目标产品，都重新从该产品的已确认 PRD 选择能力包：

- 小游戏可以选择 Game Experience，但不会改变工厂内核；
- 普通网站可以只有 Web Interface，不自动加入 Agent Runtime；
- Agent 产品才建立目标产品自己的五要素并评估 Agent Runtime；
- 大型知识库明确需要语义检索时才选择 RAG；
- 图片、音频、视频是核心输入或产物时才选择 Multimedia；
- 多用户、登录和数据隔离成为目标产品需求时才选择 Accounts and Tenancy；
- 语音、协作或双向高频通信成为核心时才选择 Realtime Communication。

工厂 Harness 的 12 项采用结论服务“生产过程”；目标产品能力包服务“被生产产品”。两者必须分别保存，不能互相推导替代。

## 9. Seam 与 Adapter 选择

| 依赖类型 | 当前依赖 | Seam 结论 | Adapter 策略 |
| --- | --- | --- | --- |
| 进程内 | 权限策略、状态转换、目标判断、上下文预算 | 保持为内部 Module，不为测试暴露额外 Interface | 直接通过所属 Module 的外部 Interface 测试 |
| 本地可替代 | SQLite、文件系统、Git、命令和目标产品工作区 | 只有存在真实本地与测试替身时建立内部 Seam | 临时目录、测试数据库或内存替身；不把内部 Seam 泄露给上层 |
| 远程但自有 | 第一版本没有独立自有微服务 | 不创建假想端口 | 保持模块化单体，出现真实远程部署再设计 |
| 真正外部 | DeepSeek、npm 软件源、未来目标产品 API | 在调用处建立受控 Seam | 生产 Adapter + 测试 Adapter / mock；错误、超时和用量统一归一化 |

现有 `AgentRuntime` 已经有 PiAgentRuntime 与 InMemoryAgentRuntime 两个 Adapter，因此是一个真实且应保留的 Seam。后续 Harness 通过 AgentRuntime 使用模型，不直接依赖 Pi Agent 或 DeepSeek 的具体事件格式。

## 10. 现有代码复用与缺口

| 现有 Module 或代码 | G4 处理 | 已具备 | 仍缺少 |
| --- | --- | --- | --- |
| AgentRuntime | 保留并加深 | Pi Adapter、内存 Adapter、事件映射、DeepSeek 配置检查 | 完整工具定义、预算、取消、上下文恢复和结构化终态 |
| ProductionController | 保留为确定性控制平面 | 空结果不能确认、阶段确认后创建下一批次 | G1–G9 完整闸门、暂停继续终止、版本失效和完成目标 |
| ProductionRunStore | 保留并迁移扩展 | 批次、事件序号、领取和状态持久化 | 任务图、租约续期、检查点、副作用和 Workflow journal |
| Worker | 用 FactoryHarness 替换内部一次性执行，不平行叠加第二套循环 | 领取批次、调用 AgentRuntime、保存事件 | 连续工具循环、后台任务、恢复、Goal Gate 和统一退出 |
| RuleBasedBlueprintCompiler | 保留现有契约，后续接入已确认 G1–G5 产物 | 游戏与非游戏画像的确定性基础 | 版本化五要素、组件选型和七层架构编译 |
| WebUI | 保留为控制平面 | 项目、运行、SSE、确认与重试入口 | 计划、工具、证据、暂停恢复和 G1–G9 产物展示 |

后续实现应“替换内部一次性执行”，不能在现有 Worker 旁边再创建另一套生产循环。这样 FactoryHarness 的复杂度集中在一个 Module，调用方仍只面对小 Interface。

## 11. 最小采用组合的失败保护

| 失败类型 | 主要负责项 | 必须得到的结果 |
| --- | --- | --- |
| 模型超时、限流或未知停止原因 | s01、s15 | 结构化失败、有限重试或安全交还用户 |
| 工具参数错误或工具不存在 | s02 | 执行前校验或统一工具错误，保持调用结果配对 |
| 越权路径、危险命令或发布请求 | s03、s04 | 拒绝或进入人工闸门，并记录审计事件 |
| Agent 忘记当前计划 | s05 | 从可见计划恢复下一项，不改变生产状态事实 |
| 无关知识挤占上下文 | s07、s08 | 按需加载并压缩普通历史，保护手册与关键事实 |
| Worker 重启或后台任务中断 | s10、s11、s16 | 从任务、journal 和检查点恢复，避免重复副作用 |
| 多机制产生不同状态 | s15 | 统一 Harness 事件与终态 |
| 模型停止但产物不完整 | s17 | 继续执行、失败或等待用户，绝不自动完成 |

## 12. 成本、外部平台与范围

本选型：

- 不新增模型供应商，继续使用已确认的 DeepSeek；
- 不新增付费平台、云资源、MCP server 或外部数据上传；
- 不引入 PostgreSQL、Redis、RAG、对象存储、多用户或多 Agent 团队；
- 不升级现有核心依赖版本；
- 不修改三份原始手册；
- 不修改生产代码和现有 SQLite 数据；
- 只为 G5 提供已确认的最小模块集合。

具体工具数量、Token、时间、步数、并发和费用上限在 G6 当前阶段开发文档中提出推荐值并由产品负责人确认。
