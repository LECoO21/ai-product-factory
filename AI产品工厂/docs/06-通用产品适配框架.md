# AI 产品工厂｜通用产品适配框架 V0.2

> 状态：适配方向已确认；详细生产流程等待正式 PRD 确认。

## 1. 通用性的定义

工厂的通用性不是准备几十个固定模板，也不是声称任何产品都能一键生成。它应做到：

- 工厂内核只理解生产、状态、权限、证据和恢复；
- 产品差异被表达为产品画像；
- 生产蓝图根据产品画像组合基础工位和能力包；
- 增加新产品形态时不修改生产控制器核心；
- 无法支持的产品能力被明确识别，而不是静默套用错误模板。

Agent Blueprint 的 Harness 组件用于建设工厂自身的执行能力，也用于目标产品本身确实是 Agent 时的产品架构；它不能把每个小游戏、网站或数据工具都强行改造成 Agent 产品。

小游戏是第一台试产样机。它用于发现真实生产问题，不拥有定义工厂领域模型的权力。

## 2. 产品画像维度

系统读取 PRD 后，从下列维度建立产品画像：

| 维度 | 示例 |
| --- | --- |
| 用户任务 | 创作内容、管理业务、娱乐、分析数据、自动执行 |
| 交互形态 | 一次提交、多轮对话、工作流确认、画布、实时操作 |
| 目标终端 | Web、移动 Web、桌面端、原生 App、小程序、API |
| 执行特征 | 短请求、长任务、流式输出、实时循环、离线运行 |
| 产物 | 文本、表格、图片、音频、视频、文件、可交互状态 |
| 数据关系 | 无持久化、单用户、账户、多租户、协作、交易 |
| AI 角色 | 仅用于开发、产品核心能力、辅助能力、完全不在运行时使用 |
| 风险 | 低成本生成、付费调用、外部发送、删除、发布、监管数据 |
| 质量判断 | 确定性测试、模型效果、视觉体验、可玩性、业务准确率 |
| 部署要求 | 本地、公网、云平台、公司环境、应用商店或特定平台 |

“游戏”“SaaS”“Agent”可以作为方便用户理解的标签，但不能直接决定流水线。

## 3. PRD 到生产蓝图的五步编译

每个产品必须按固定顺序形成可确认方案：

1. **需求拆解**：提取目标、用户、核心闭环、交付物、边界和约束；缺失项标“待确认”，不脑补。
2. **领域建模**：映射为工具、知识、观察、行动和权限五要素。
3. **组件选型**：同时选择工厂 Harness 组件和目标产品能力包；没有明确必要性就不选择。
4. **架构设计**：产出交互、产品、Agent 编排、模型、能力集成、数据和基础设施七层架构。
5. **代码生产**：只有方案人工确认后，才按骨架、硬化、产品化三个层次生成代码。

对于不含运行时 AI 的产品，七层架构中的“模型层”和目标产品“Agent 编排层”可以标记为无；工厂自身的 Agent Harness 仍负责生产过程。

## 4. 通用基础工位

所有数字产品默认继承：

1. 接单与资料体检；
2. 产品范围确认；
3. 技术适配；
4. 阶段设计；
5. 实现；
6. 自动质量检查；
7. 真实产品验收；
8. 发布准备；
9. 部署与上线验收（当前阶段需要时）。

这些是生产责任，不代表必须表现为九个固定页面或九次 Agent 调用。生产蓝图可以按产品复杂度合并工位。

## 5. 第一批能力包

| 能力包 | 触发条件 | 追加的关键要求 |
| --- | --- | --- |
| Web 界面 | 目标终端包含 Web | 响应式、无障碍、浏览器 E2E |
| Agent | 产品运行时调用模型或工具 | Prompt 版本、输出校验、成本、真实模型冒烟 |
| 长任务 | 执行可能跨请求或超过短等待 | 持久化任务、进度、取消和恢复 |
| RAG | 知识库、文档问答或语义检索 | 数据摄取、召回评估、引用和权限 |
| 多媒体 | 图片、音频或视频输入输出 | 上传安全、对象存储、预览和处理失败 |
| 游戏体验 | 实时交互、规则循环或可玩性 | 帧循环、输入、状态重开、试玩和性能 |
| 账户与多租户 | 多用户数据或权限 | 鉴权、授权、数据隔离和审计 |
| 高风险动作 | 付费、发布、发送、删除或外部写入 | 幂等、预算、人工确认和审计 |
| 实时通信 | 双向高频或多人同步 | 连接状态、重连、一致性和压力验证 |

能力包可以叠加。例如“带 AI NPC 和账号存档的小游戏”会组合 Web、游戏体验、Agent、账户和长任务能力包。

## 6. 示例蓝图

### 普通小游戏

```text
通用基础
+ Web 界面
+ 游戏体验
```

如果模型只参与开发，不在玩家游玩时调用，就不启用 Agent 运行时产品要求。

### AI 内容生成工具

```text
通用基础
+ Web 界面
+ Agent
+ 长任务
+ 多媒体（如生成图片或视频）
+ 高风险动作（如真实扣费明显）
```

### 内部数据工作台

```text
通用基础
+ Web 界面
+ 账户与多租户
+ Agent（如自然语言分析）
+ 高风险动作（如写回业务系统）
```

### API 产品

```text
通用基础
+ 账户与配额
+ Agent（按实际能力）
+ 长任务（按执行时长）
```

它不应因为工厂默认使用 WebUI，就被强迫生成面向最终用户的 Web 前端。

## 7. 蓝图编译规则

```text
读取 PRD、现有代码和三份原始手册
→ 提取需求硬事实与产品画像
→ 建立 Harness 五要素
→ 检查强制底线
→ 选择最小 Agent Blueprint 组件与产品能力包
→ 生成标准七层架构、Workflow 和质量闸门
→ 标记当前工厂尚不支持的能力
→ 由产品负责人确认方案、重大范围和成本
→ 确认后才开始代码生产
```

蓝图是每个产品项目的版本化产物。PRD、终端、风险或交付范围显著变化时重新编译，新版本不能悄悄改变已经运行的生产批次。

## 8. 通用性验收

工厂 MVP 除小游戏试产外，还必须通过以下检查：

- 用一个非游戏产品画像生成第二条蓝图；
- 两条蓝图共用同一个生产控制器和生产事件结构；
- 核心数据库不存在 `level`、`score`、`npc` 等产品专属字段；
- 关闭游戏能力包后，不加载游戏工位、工具和验收项；
- 新增能力包通过注册和 schema 校验接入，不修改控制器状态机；
- 不含运行时 AI 的产品不会被强行加入 Agent、Memory、MCP 或团队组件；
- 目标产品是 Agent 时，蓝图包含其自己的五要素、组件选型、工具权限和完成目标；
- 遇到原生 App、硬件或强监管等暂不支持能力时，系统明确报告缺口和建议路线。

只有通过这组验证，小游戏试产成功才可以被解释为“工厂路线成立”，而不是“我们做出了一个小游戏生成器”。
