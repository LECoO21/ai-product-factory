## 一、项目判断与适配结论

- 产品类型：本地单用户使用的 AI 数字产品生产工作台。
- 主要终端：桌面 Web，完整兼顾 390px 移动 Web。
- 项目性质：已有 Next.js 16 + React 19 + TypeScript strict 项目，继续增量开发，不重建平行前端。
- 本阶段目标：用户从需求输入进入真实生产批次后，能够看懂状态、等待原因、结果、产物和下一步；刷新、失败、断线、确认、重试、调整和停止都不丢失后端事实。
- 样式策略：继续使用 Naxe 现有语义 CSS 变量和原创组件，不更换品牌、不复制参考站资产、不为形式统一重构为另一套组件库。
- 状态策略：SQLite/API 是最终事实来源；URL 保存项目与批次 ID；组件 State 只保存输入、提交中和局部展开状态。
- 通信策略：普通请求使用统一 API Client；运行事件使用统一 SSE Adapter；断线后先查询真实状态，再决定是否恢复连接。
- 测试策略：Vitest + React Testing Library + Playwright；自动化测试不能替代真实后端和真实浏览器验收。
- 部署策略：本阶段只做本地前端质量闭环，不进入第三份手册，不部署。

## 二、现状检查

### 2.1 已具备

- App Router、Server/Client Component 基本边界；
- 首页需求输入器、产品历史、产品页和运行页；
- 真实 SQLite 数据、Route Handler、SSE 和刷新恢复；
- 真实等待确认、重试、调整、停止和 Harness 产物；
- 390px、1280px、1440px 已有真实浏览器验证；
- Lint、TypeScript、Vitest 和生产构建已配置。

### 2.2 必须补齐

1. `fetch` 与 `EventSource` 仍散落在多个组件中，不符合集中式 API 层要求；
2. API 错误返回结构不统一，组件各自解释字符串或对象；
3. 后端状态直接进入页面，没有统一的前端任务状态与未知状态兜底；
4. SSE 断线后直接关闭，缺少“查询真实状态 → 按序号恢复”的统一策略；
5. 运行页仍显示 `succeeded` 等内部词，结果、产物和执行详情的层级需要进一步产品化；
6. 没有 React 组件测试和 Playwright 核心业务 E2E；
7. 768px、键盘操作、刷新恢复、断线状态和重复点击还没有成为固定回归门槛。

## 三、本阶段范围

### 3.1 包含

#### A. 集中式请求与错误层

- 新建 `apps/web/lib/api/`：统一 JSON 请求、超时、错误归一化和运行时校验；
- 前端统一错误结构：`code / userMessage / retryable / requestId / fieldErrors`；
- 新建产品、启动、查询、确认、重试、调整和停止都通过业务 API 函数调用；
- 展示组件中不再直接拼接接口和解释原始错误；
- DeepSeek Key、数据库路径和内部 Prompt 始终只在服务端。

#### B. 统一任务状态

前端统一状态：

```text
idle / submitting / queued / running / streaming / waiting_user /
succeeded / failed / cancelled / disconnected / stale
```

后端映射：

| 后端事实 | 前端状态 | 用户看到什么 |
| --- | --- | --- |
| 尚未创建批次 | `idle` | 输入需求或开始生产 |
| 提交请求中 | `submitting` | 正在提交，按钮不可重复点击 |
| `ready` | `queued` | 已受理，等待开始 |
| `running` | `running` / `streaming` | 正在执行，展示真实活动与已产生结果 |
| `waiting_approval`、`waiting_user`、`blocked` | `waiting_user` | 明确需要用户确认、补配置或补资料 |
| `succeeded` | `succeeded` | 结果和产物已完成 |
| `failed` | `failed` | 失败原因、保留结果和可恢复动作 |
| `cancelled` | `cancelled` | 已停止，已有记录仍保留 |
| SSE 中断且后端仍活动 | `disconnected` | 连接中断，正在恢复；不宣称任务停止 |
| 未知枚举或状态可能过期 | `stale` | 状态需要刷新，不猜成功或失败 |

#### C. 运行页产品化

- 顶部状态区回答：现在发生什么、用户要做什么、接下来会发生什么；
- 结果和产物在前，工具轨迹和内部执行详情默认折叠；
- 页面不直接显示 `succeeded`、Pi、Worker 等内部词；
- 人工确认区说明已完成内容、确认原因、确认后的影响和“本阶段不会部署”；
- 失败时保留已有结果，展示能否重试和重试影响；
- 运行时只展示真实可用的调整与停止；停止后不伪装成浏览器请求取消；
- Artifact 统一展示名称、类型、状态、大小和查看入口；生成中或失败产物不伪装为完成。

#### D. 断线、刷新和防重复

- SSE 使用最后事件序号恢复，事件按 sequence 去重；
- 断线后先调用运行查询接口，终态不重连，活动态按退避有限重连；
- 页面不可见时不增加高频轮询；
- 刷新页面从 URL 批次 ID 和后端事实恢复；
- 创建、开始、确认、重试、调整和停止在提交中禁用重复操作；
- 调整和停止继续使用幂等键；确认与重试继续由后端保证幂等。

#### E. 响应式与无障碍

- 固定验收 390、768、1280、1440px；
- 手机端导航、状态、结果、确认和输入均可触达，无透明遮挡和横向溢出；
- 核心操作可用键盘完成，表单有 Label，焦点样式清楚；
- 状态不只依靠颜色；动态状态使用克制的 live region；
- 尊重 `prefers-reduced-motion`。

#### F. 自动化与真实验收

- 单元测试：状态映射、错误归一化、事件去重和断线决策；
- 组件测试：需求输入、提交禁用、确认条件、失败恢复、产物展示；
- Playwright：核心流程、刷新恢复、重复点击、失败批次无确认按钮、四档宽度和键盘操作；
- E2E 使用隔离测试数据库验证真实 Route Handler 与页面，不把静态 Mock 当完成；
- 最终再使用已经完成的真实 DeepSeek Harness 批次验证真实结果页，不额外产生模型费用；
- 浏览器 Console 无应用错误，Network 无无界重复请求。

### 3.2 不包含

- 不改写 G6 FactoryHarness、ToolGateway 或完成目标；
- 不引入多租户、登录、计费、埋点、国际化或全局状态库；
- 不开发小游戏或其他目标产品；
- 不实现完整 Workflow checkpoint；
- 不执行 Git commit、push、远端写入或部署；
- 不进入第三份《上线部署手册》。

## 四、页面与组件

- `/`：需求输入、待处理任务、最近产品；
- `/projects/new`：完整需求输入；
- `/projects/[id]`：产品档案和继续入口；
- `/runs/[id]`：统一任务状态、结果、产物、确认和执行详情。

### 4.2 新增或调整的模块

```text

├── lib/api/                    # request、AppError、schema

```

| 页面/模块 | 初始 | 加载 | 空 | 运行 | 等待确认 | 成功 | 失败 | 恢复 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 需求输入器 | 可输入 | 提交禁用 | 输入限制提示 | 不适用 | 不适用 | 进入产品页 | 保留输入并显示字段/通用错误 | 可重新提交 |

| 运行页 | 读取批次 | 明确加载 | 结果尚未产生 | 活动、增量结果、控制 | 完成内容、影响、确认按钮 | 结果与产物 | 原因、保留事实、恢复动作 | SSE 按序恢复、刷新重读 |

## 六、接口契约范围

| 业务动作 | 接口 | 成功 | 主要错误 | 幂等/重试 |
| --- | --- | --- | --- | --- |
| 创建产品 | `POST /api/projects` | `project` | 字段错误、创建失败 | 提交中禁用；超时后先查项目 |
| 启动批次 | `POST /api/projects/:id/runs` | `run` | 项目不存在、创建失败 | 提交中禁用 |
| 查询批次 | `GET /api/runs/:id` | `run/events/harness` | 不存在、读取失败 | 可安全重试 |
| 事件恢复 | `GET /api/runs/:id/events?after=` | 后续事件 | 断线、不存在 | 按 sequence 去重和恢复 |
| 确认继续 | `POST /api/runs/:id/approve` | 当前批次、下一批次 | 尚无结果、状态不允许 | 后端幂等 |
| 重试 | `POST /api/runs/:id/retry` | 新批次 | 状态不允许 | 后端防重复 |
| 调整 | `POST /api/runs/:id/steer` | receipt | 非活动、输入错误 | idempotencyKey |
| 停止 | `POST /api/runs/:id/abort` | receipt | 非活动、输入错误 | idempotencyKey |

本阶段会统一 Route Handler 的错误外形，但不向浏览器暴露堆栈、供应商原始错误、密钥或完整 Prompt。

## 七、验收步骤

1. 新建产品：输入少于 20 字会在字段附近提示；合法需求只创建一个产品；
2. 启动生产：按钮提交中不可重复点击；页面显示已受理、运行或真实终态；
3. 运行恢复：运行页刷新后状态、结果、产物和计划仍存在；
4. 断线恢复：断开 SSE 后页面显示连接中断，不宣称失败；恢复时不重复事件；
5. 人工确认：结果与必需产物齐全后才显示业务确认按钮；失败或空结果没有确认按钮；
6. 失败恢复：失败原因清楚，已有结果不消失，可重试时说明会创建新批次；
7. 真实结果：G6 成功批次显示首次失败、修复复测通过和三个真实产物；
8. 响应式：390、768、1280、1440px 无无意横向滚动，核心按钮可触达；
9. 键盘：从输入到提交、查看结果、展开详情和确认均可操作；
10. 质量检查：`manuals:verify`、lint、typecheck、test、build、Playwright 全部通过；
11. 浏览器 Console 无应用错误，Network 无失败风暴或重复创建任务；
12. `.env`、密钥、三份手册全文、SQLite 和 `data/` 不进入提交。

## 八、风险与回退

- 风险：集中 API 与 Stream 后可能改变现有刷新时机。处理：先用状态与恢复测试冻结行为，再逐组件迁移。
- 风险：SSE 重连造成重复事件。处理：使用 sequence 去重，重连前查询真实状态。
- 风险：组件拆分导致视觉变化。处理：保留现有 Naxe token，以浏览器截图对比检查代表页。
- 风险：E2E 污染真实数据。处理：使用独立临时数据库和独立服务端口。
- 回退：每次迁移保持现有 Route Handler 和数据库契约，任何一层失败都可回到原组件调用，不修改历史生产记录。
